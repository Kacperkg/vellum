# Authentication backend-writer transition safety

## Assessment and scope

PR #28 changes authentication/session validity and starts GORM AutoMigrate before binding the API listener. It requires all old backend writers to stop before the new backend starts, even when SES sending is disabled. `PASSWORD_RESET_EMAIL_MODE=disabled` does not disable migrations, version checks or reset redemption.

The preceding controller checked the manifest/bundle, PostgreSQL readiness, both image digests/platform/revision labels, then called `docker compose up -d --no-deps --no-build --pull never --wait ... backend frontend`. Docker documents ordinary changed-service replacement as stopping/recreating containers and preserving mounted volumes. The problem is **no explicit all-writer barrier or verification**: stale scaled replicas or a `compose run` one-off could survive normal replacement. Health checks and host locks alone do not prove old writers are absent.

The shared staging/production controller keeps all existing provenance checks before downtime and adds:

1. Enumerate all containers with exact target project `vellum-staging` or `vellum-production` and service `backend` labels, including stopped, restarting and one-off instances. Validate full container IDs and inspected identity. Ambiguous paused/dead/removing states fail for operator recovery.
2. Stop those exact IDs with a 30-second grace period. Verify each is exited/created with PID zero, not running/restarting/paused/dead. Do not start anything if stop/inspection fails.
3. Remove only verified stopped backend containers using non-forced `docker container rm`, without `-v`/`--volumes`. This removes stale restart paths, including restart-always containers. Retain their images, current/previous/per-release receipts and all volumes. Re-enumerate and require no target backend containers remain.
4. Read only the count of other client sessions in the target environment database through its existing PostgreSQL container; exclude the checker itself. Wait up to a 15-second polling window, with each command bounded to five seconds, then fail closed. Previously submitted database work may outlive the application process. Maintenance clients must disconnect too. Do not terminate sessions, read SQL text or touch the other environment's separate database.
5. Start backend/frontend through the existing digest-pinned, no-dependencies/no-build/no-pull Compose command, with either environment explicitly scaled to one backend. Verify exactly one ordinary healthy running backend uses the requested digest. Run the unchanged Caddy/API/frontend/auth smoke before recording success.

The entire sequence remains under the existing host-wide operation locks and durable pending record. Lock order/inodes, recovery-marker format, SSM document, IAM, production approval, manifest schema and bundle-hash validation are unchanged. Both environments execute the same barrier. Production still requires its verified staging artifact and fresh release-specific backup/restore/schema/proxy approval; its workflow remains disabled pending separate activation approval.

This is a managed-path guarantee. All application writers must use the reviewed target Compose project/service labels and protected configuration; no uncoordinated manual/external database writers may connect during rollout. Root/Docker administrators can bypass service labels and advisory locks, so an operator freeze is required. The check does not claim isolation from a compromised host administrator or prevent an unlabelled external writer from reconnecting after observation.

The production extension reuses the same barrier, including database-session draining and singleton verification, on every managed production release. It accepts a brief production API outage to exclude version-unaware writers before AutoMigrate. It does not authorize production workflow activation, deployment or merge. Production runs at 02:15 UTC, staging at 03:15 UTC; `Persistent=true` may cause catch-up on enable/boot. This patch changes no timer. Drain ongoing controller, Docker/Compose, dump and migration work; cancellation or an unlocked flock is insufficient. Resolve any pending marker through approved recovery first, never by automatic deletion.

Membership remains six files; even an older six-file PR #28 installation is incompatible because the controller hash changes. Never patch receipt/manifest hashes to bypass this check. Preserve the prior bytes and known-good images privately. No controller daemon restart is required.

4. Before migration, take a fresh production backup, verify its off-host copy and prove restore in an isolated environment. Review representative migration DDL, lock/duration impact and the existing budget-uniqueness preflight in `backend/internal/database/migrate.go`. It polls for up to 15 seconds with each observation bounded to five seconds, never kills sessions or reads SQL text. A remaining session or failed observation retains the pending gate and prevents startup. It never drains staging's database. Preserve the disabled production workflow until its separate activation work is approved. 8. Before resuming managed host jobs/timers, verify production health and version-aware login/refresh/logout/recovery with approved test accounts, receipt consistency and the absence of unfinished work. Timer coordination does not authorize changing backup schedules or bypassing freshness/restore/alert gates. A retained pending marker blocks both deployments and backups; respond promptly to protect backup coverage.

Production uses the failure/recovery procedure below with **production** as the target. Timeouts bound individual Docker/SQL calls, not the entire migration or daemon operation. Image pulls and a large inventory can exceed SSM's existing 900-second limit; timeout requires investigation and retains the marker. No automated old-code rollback, session termination or recovery-marker cleanup is added.

## Failure, cancellation and recovery

Before the operation context, a manifest/bundle mismatch stops without service mutation. Inside the context, any stop/inspect/remove/database-drain/start/health/smoke/receipt failure retains the pending marker. A failure before receipt persistence (including stop/start/migration/health/smoke failure) leaves success receipts unchanged and never automatically restarts/recreates the previous image. Receipt files are written sequentially after smoke, not as one multi-file transaction: a later write/fsync failure or cancellation can leave some pointers updated while the pending marker remains; operators must reconcile every receipt against actual runtime state. Old containers may still exist if stopping/removal failed. If startup occurred, a candidate may remain running/unhealthy/restarting and continue retrying AutoMigrate under `unless-stopped`; an API outage, stale receipt or controller exit does not prove database quiescence.

GORM AutoMigrate is not one globally atomic migration. An error may leave additive DDL or seeded data even without a healthy API. There are no down migrations. A Docker/SSM request can outlive timeout/cancellation, and SIGKILL/reboot retains the marker even though kernel locks are released. The next managed backup/deployment/maintenance operation must refuse the marker until approved recovery. Do not add automatic rollback or an automatic marker cleanup.

For recovery, retain the marker and freeze new operations. Privately inspect the exact SSM command, Docker daemon/Compose work, every target backend instance including one-offs, actual digests/health, and target DB sessions/transactions/migration state. Drain all work; if necessary explicitly approve stopping/removing a failed candidate and verifying DB quiescence under the existing recovery procedure. Preserve PostgreSQL and volumes. Do not use `down`, `down -v`, volume/image prune, database replacement or unrelated-service/Caddy restart.

Only after an operator proves quiescence may the existing [pending recovery procedure](HOST-COORDINATION.md) clear the marker while holding the original lock inodes. Prefer a newly reviewed version-aware roll-forward/recovery release with the currently installed matching bundle. It re-enters the same barrier and must pass health/smoke before new receipts are trusted. Unchanged historical receipts describe the last successful deployment, not necessarily the currently running image after failure.

A genuine pretransition receipt carries the old controller hash, so the new controller rejects it before mutation. **Never downgrade the controller or rewrite hashes to revive version-unaware backend code.** Schema compatibility does not preserve session revocation: old middleware can accept revoked access JWTs. An exceptional old-code rollback would require a separately designed, independently reviewed and explicitly approved security/data migration (traffic freeze, fresh recoverable backup, complete writer/session invalidation and current tooling/provenance compatibility); rotating a secret alone is not authorization or a supported bypass. Do not restore a stale financial backup merely to undo application code.
