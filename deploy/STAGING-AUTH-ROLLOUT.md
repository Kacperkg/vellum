# Staging password-recovery controller compatibility

## Assessment and scope

PR #28 changes authentication/session validity and starts GORM AutoMigrate before binding the API listener. It requires all old backend writers to stop before the new backend starts, even when SES sending is disabled. `PASSWORD_RESET_EMAIL_MODE=disabled` does not disable migrations, version checks or reset redemption.

The preceding controller checked the manifest/bundle, PostgreSQL readiness, both image digests/platform/revision labels, then called `docker compose up -d --no-deps --no-build --pull never --wait ... backend frontend`. Docker documents ordinary changed-service replacement as stopping/recreating containers and preserving mounted volumes. The problem is **no explicit all-writer barrier or verification**: stale scaled replicas or a `compose run` one-off could survive normal replacement. Health checks and host locks alone do not prove old writers are absent.

The focused staging change keeps all existing provenance checks before downtime and adds:

1. Enumerate all containers with exact project `vellum-staging` and service `backend` labels, including stopped, restarting and one-off instances. Validate full container IDs and inspected identity. Ambiguous paused/dead/removing states fail for operator recovery.
2. Stop those exact IDs with a 30-second grace period. Verify each is exited/created with PID zero, not running/restarting/paused/dead. Do not start anything if stop/inspection fails.
3. Remove only verified stopped backend containers using non-forced `docker container rm`, without `-v`/`--volumes`. This removes stale restart paths, including restart-always containers. Retain their images, current/previous/per-release receipts and all volumes. Re-enumerate and require no staging backend containers remain.
4. Read only the count of other client sessions in the staging database through its existing PostgreSQL container; exclude the checker itself. Wait up to a 15-second polling window, with each command bounded to five seconds, then fail closed. Previously submitted database work may outlive the application process. Maintenance clients must disconnect too. Do not terminate sessions, read SQL text or touch production's separate database.
5. Start backend/frontend through the existing digest-pinned, no-dependencies/no-build/no-pull Compose command, with staging explicitly scaled to one backend. Verify exactly one ordinary healthy running backend uses the requested digest. Run the unchanged Caddy/API/frontend/auth smoke before recording success.

The entire sequence remains under the existing host-wide operation locks and durable pending record. Lock order/inodes, recovery-marker format, SSM document, IAM, production approval, manifest schema and bundle-hash validation are unchanged. Production replacement behavior is unchanged; this is not production deployment readiness approval.

This is a managed-path guarantee. All application writers must use the reviewed staging Compose project/service labels and protected configuration; no uncoordinated manual/external database writers may connect during rollout. Root/Docker administrators can bypass service labels and advisory locks, so an operator freeze is required. The check does not claim isolation from a compromised host administrator or prevent an unlabelled external writer from reconnecting after observation.

## Merge and installation decision

The compatibility change belongs in PR #28 because it is required for that authentication transition and preserves existing release contracts. Code is suitable for review/merge only after required CI and reviewer gates pass. **With staging CD active, install/verify the matching six-file controller bundle before merging**; merging is a release trigger. The old installed bundle rejects the new candidate hashes before service mutation, so merging before installation fails closed but is not a working rollout plan.

No host installation or live-state inspection was performed by this task. The repository documents the intended installed paths; it cannot certify the bytes currently installed on EC2. Installation and rollout remain separately approved operator actions.

Install from the exact reviewed PR revision as inert data under a drained host maintenance freeze:

- `/usr/local/lib/vellum-cd/compose.yml`
- `/usr/local/lib/vellum-cd/compose.registry.yml`
- `/usr/local/lib/vellum-cd/cd/controller.py`
- `/usr/local/lib/vellum-cd/cd/coordination.py`
- `/usr/local/lib/vellum-cd/cd/release.py`
- `/usr/local/lib/vellum-cd/cd/smoke.py`

Compare all six installed SHA-256 hashes with the approved source and eventual release manifest; retain the prior installed bytes privately as evidence, not as tooling to replay old receipts. Verify root ownership, regular files 0644, directories 0755, and the existing root-private 0700 state/config directories and 0400/0600 singly-linked runtime files. Use the trusted staging-directory installation procedure in [CI-CD.md](CI-CD.md) and [HOST-COORDINATION.md](HOST-COORDINATION.md). Never execute checkout code as root. No backup script/unit, timer, AWS, SSM, IAM, DNS or GitHub-setting change is required for this controller fix. Do not replace runtime credentials, project names or volumes.

PR #28 also requires the reviewed recovery endpoint Caddy matchers/privacy headers and Compose environment forwarding from [PASSWORD-RESET.md](PASSWORD-RESET.md). An operator must merge/validate those Caddy changes separately if not already installed; preserve other sites and reload only after approval. The controller neither modifies nor restarts Caddy. SES may remain disabled throughout the initial rollout.

## Exact controlled rollout order

These steps are instructions for future approved operations; none were executed on a live host here.

1. **Approval: host installation window.** Freeze staging merges/dispatches and overlapping deployment, backup, restore and migration work across the shared host using the existing operational process. Drain current Actions/SSM/controller/Compose work; cancellation alone does not prove it stopped. Confirm the pending marker is absent, or complete the documented approved recovery first. Never delete lock files or clear an uncertain marker. Production traffic/containers and Caddy remain running; no production deployment is performed.
2. Privately record the current staging backend image digests/revisions, PostgreSQL container/volume identities and successful receipts. Preserve previous known-good images and recovery evidence. Take a separately approved fresh staging backup and verify restore in isolation; two-day retention alone is not restore proof. Measure/review migration behavior and accept a brief staging API outage. Do not change database credentials or volumes.
3. Stage and verify the exact six reviewed files outside the writable checkout, then install them at the protected paths above under the approved drained maintenance procedure. Preserve host coordination and root-owned runtime configuration. Confirm old entry points cannot mutate staging outside the managed path. There is no controller daemon to restart and no database restart is needed.
4. Validate the installed Compose model privately using the existing synthetic/quiet validation procedure; do not print resolved secrets. Confirm exact staging origin, private backend/database ports, existing project/volume identity and Caddy proxy trust. Keep SES disabled. Merge/validate the PR's Caddy examples only through the separately approved proxy procedure if needed. Disconnect staging maintenance/monitoring SQL clients for the database drain gate.
5. **Approval: merge/release.** After required PR CI and review pass and installed hashes match, authorize merging PR #28 into staging. This task does not merge. Let the existing staging pipeline build a fresh candidate, run required checks, publish immutable digests and dispatch its pinned SSM document. Do not replay a historical run or rewrite manifest/receipt hashes. Any final reviewed source changes affecting the bundle require renewed installed-hash verification.
6. The installed controller validates the manifest and matching bundle before mutation, takes the existing host locks, writes/fsyncs `operation-pending.json`, validates protected config, checks the existing PostgreSQL container/readiness, pulls and checks both images, then executes the stop/verify/remove/empty-inventory/database-drain barrier above. Only then does it start exactly one new backend and update the frontend. PostgreSQL, all volumes, production containers and Caddy are excluded from mutations.
7. During the gap, staging API requests may fail with an unavailable/502 response; the frontend/proxy may remain accessible. New startup runs AutoMigrate/seeding before `/ping` can succeed. Compose waits for existing health checks; successful backend health proves startup returned from migration but is not a substitute for smoke. The controller checks singleton/health/digest and existing Caddy/auth/rate-limit smoke, then writes current/previous/per-release success receipts. Only complete success clears/fsyncs the pending marker. The workflow's existing verified-artifact procedure remains unchanged.
8. Privately verify version-aware login/refresh/logout, protected routes and recovery pages with SES disabled; actual email delivery is a separate approval/runbook step. Record evidence and resume managed host jobs only after the existing health/recovery/backup gates allow it. Do not enable production sending or production workflows as part of staging acceptance.

## Failure, cancellation and recovery

Before the operation context, a manifest/bundle mismatch stops without service mutation. Inside the context, any stop/inspect/remove/database-drain/start/health/smoke/receipt failure retains the pending marker. A failure before receipt persistence (including stop/start/migration/health/smoke failure) leaves success receipts unchanged and never automatically restarts/recreates the previous image. Receipt files are written sequentially after smoke, not as one multi-file transaction: a later write/fsync failure or cancellation can leave some pointers updated while the pending marker remains; operators must reconcile every receipt against actual runtime state. Old containers may still exist if stopping/removal failed. If startup occurred, a candidate may remain running/unhealthy/restarting and continue retrying AutoMigrate under `unless-stopped`; an API outage, stale receipt or controller exit does not prove database quiescence.

GORM AutoMigrate is not one globally atomic migration. An error may leave additive DDL or seeded data even without a healthy API. There are no down migrations. A Docker/SSM request can outlive timeout/cancellation, and SIGKILL/reboot retains the marker even though kernel locks are released. The next managed backup/deployment/maintenance operation must refuse the marker until approved recovery. Do not add automatic rollback or an automatic marker cleanup.

For recovery, retain the marker and freeze new operations. Privately inspect the exact SSM command, Docker daemon/Compose work, every staging backend instance including one-offs, actual digests/health, and staging DB sessions/transactions/migration state. Drain all work; if necessary explicitly approve stopping/removing a failed candidate and verifying DB quiescence under the existing recovery procedure. Preserve PostgreSQL and volumes. Do not use `down`, `down -v`, volume/image prune, database replacement or production/Caddy restart.

Only after an operator proves quiescence may the existing [pending recovery procedure](HOST-COORDINATION.md) clear the marker while holding the original lock inodes. Prefer a newly reviewed version-aware roll-forward/recovery release with the currently installed matching bundle. It re-enters the same barrier and must pass health/smoke before new receipts are trusted. Unchanged historical receipts describe the last successful deployment, not necessarily the currently running image after failure.

A genuine pretransition receipt carries the old controller hash, so the new controller rejects it before mutation. **Never downgrade the controller or rewrite hashes to revive version-unaware backend code.** Schema compatibility does not preserve session revocation: old middleware can accept revoked access JWTs. An exceptional old-code rollback would require a separately designed, independently reviewed and explicitly approved security/data migration (traffic freeze, fresh recoverable backup, complete writer/session invalidation and current tooling/provenance compatibility); rotating a secret alone is not authorization or a supported bypass. Do not restore a stale financial backup merely to undo application code.
